# Evidence Doctrine — when a number is actually evidence

Cross-cutting. The PL, the Engineer and the Auditor all produce numbers and
all consume each other's, so these rules live once, here, and each role
file points at the section that applies at the moment that role needs it:
`.claude/skills/forge/SKILL.md`, `.claude/agents/forge-engineer.md`,
`.claude/agents/forge-auditor.md`.

Every rule below came from an observed failure on a real increment, and the
incident is recorded with it deliberately. A reader arriving here has no
memory of any of them, and a rule without its mechanism erodes into ritual.

The single idea underneath all five: **a number is not evidence because it
is precise, because it was really measured, or because it came out the way
you expected. It is evidence only when it can be shown to be about the
thing under test.**

## Voice

**A claim you measured and a claim you inferred must not read alike.**

Observed: a PID stated that four affected form submissions were "ordinary
buttons on the editor page". Three of them were. The fourth was reachable
by no browser gesture at all. The rest of that PID section had been
measured — the author had driven real requests to establish it — and that
one line had been inferred from reading a template. Both were written in
the same flat declarative voice, so nothing marked the inferred line as
weaker than the measured ones around it. An Engineer discovered it
mid-implementation, when the interaction it described turned out not to
exist.

Inference is legitimate and often necessary. Presenting it in the voice of
measurement is what does the damage: the next reader has no way to know
which claims to re-check, so they re-check none of them.

- **When you write:** mark inference as inference, in the sentence itself —
  "from reading the template, expected to be X; not driven." One clause is
  enough. Measured claims say what was measured and how.
- **When you read and find an unmarked inference that turns out to be
  wrong:** report it, do not quietly work around it and do not silently
  resolve it in either direction. An Engineer reports it to the PL as a PID
  defect; an Auditor raises it as a finding. The point is that the PID gets
  corrected, not that this one dispatch survives it.

## Provenance

**Name the construction path alongside the number.**

Observed: three ways of constructing what was described as "the same"
campaign produced 75,442, 85,251 and 97,788 bytes. All three were genuinely
measured — none was estimated or fabricated. But only one construction path
is the one a user actually takes: the editor's whitespace pretty-printer
runs only in the browser, so the two figures produced without a browser
were measuring an artifact no user ever receives. Only the browser figure
was valid evidence about the product.

A measurement is only as authoritative as the thing it measured. "Same
thing, measured three ways" is almost always three different things.

- **When you report a number:** say what produced the artifact you
  measured — driven in a real browser, generated by a server-side call, or
  constructed by a script — not just the number and its units.
- **When two measurements of "the same thing" disagree:** that disagreement
  is the finding, not noise to average or to pick a winner from. Establish
  which construction path a user actually takes, and report that figure,
  saying explicitly that the others measured a different path.

## Attribution

**A number that includes contributions from things that were never under
test is not evidence, however precise.**

Observed: an Auditor measured en-dash bytes in an exported file to prove a
decoder fix. The first run counted bytes across the whole export, including
server-rendered content that had never been affected by the bug and could
not have been fixed by the change — so the count could not distinguish a
working fix from a broken one. The Auditor caught this itself, re-ran with
the unaffected content stripped out, and added an empty-campaign control:
`head 2 bytes / 0 mojibake, base 0 / 2`. That second run was evidence; the
first was arithmetic.

- **When you construct a measurement:** state what population it counts and
  what it excludes. If part of the population was never under test, remove
  it before measuring, not after the number looks good.
- **When you cannot cleanly separate the populations:** add a control — a
  minimal or empty case whose expected value is known — so the number has
  something to be read against. A single control case is usually cheaper
  than arguing about attribution afterwards.

## Refutations

**"I tested it and it failed" is a claim, and gets the same scrutiny as "I
tested it and it worked."**

Observed: a PL hypothesised that a pretty-printer explained a file-size
discrepancy, tested the hypothesis, measured its effect as "a few hundred
bytes against a ~12,500 byte gap", and recorded the cause as *unexplained*.
Refusing to assert an unverified hypothesis was correct, and the honest
wording made the entry look careful. The refutation itself was wrong twice
over: it counted the wrong population (it missed that the pretty-printer
also runs over server-rendered content on load) and it valued a boundary at
one character when indentation made it about 137. The mechanism had been
the right explanation the whole time.

A negative result feels self-limiting — it claims less, so it invites less
challenge — and that is exactly why it slips through. Sounding
appropriately humble is not verification.

- **Before recording a cause as unexplained or a hypothesis as refuted:**
  apply Provenance and Attribution above to the refuting measurement. State
  what population you counted and what you assumed each unit was worth.
  Those are the two places this specific failure happened, and they are
  cheap to state.
- **When a refutation later turns out to be wrong:** correct it where the
  original claim is cited, per
  `docs/FORGE-NORTH-STAR.md#durable-truth`.

## Non-vacuity

**The question is not "did this pass" but "could this have passed by
accident."**

Observed: a fix stopped UTF-8 corruption inside a base64-encoded blob. Had
that blob happened to contain no multi-byte characters, every acceptance
criterion would have passed cleanly while the defect stayed live — the
checks would have been vacuously true. The Auditor closed this before
trusting anything else: it confirmed the served blob still carried 48
non-ASCII bytes and no escape sequences (the input genuinely still contains
the thing under test), and it ran an in-browser differential showing the
*old* expression still corrupted that exact payload (the check genuinely
still fails against the unfixed code).

Those two steps are the general shape:

1. **The input still exercises the defect.** Confirm the payload, fixture
   or page actually contains the condition the fix addresses.
2. **The check can still fail.** Run the pre-fix behaviour against that
   same input and observe it failing.

Only after both does "it passed" carry information.

**The same question applied to a test suite.** An Auditor established that
no pre-existing test was anchored to the shipped values by forcing the
constants to five different value pairs and confirming the suite responded.
The Engineer-side form of this — revert your own fix, re-run your own new
tests, report how many actually fail — is rule 14 in
`.claude/agents/forge-engineer.md`.

- **When non-vacuity cannot be established:** say so plainly rather than
  reporting a pass. Either strengthen the input until the check can fail,
  or record explicitly which gate is actually load-bearing for that
  criterion — frequently the real browser, not the test suite. A check that
  cannot fail is not a weak pass; it is not a pass at all.
