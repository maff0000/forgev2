# Evidence Doctrine — when a number is actually evidence

Cross-cutting. The PL, the Engineer and the Auditor all produce numbers and
all consume each other's, so these rules live once, here, and each role
file points at the section that applies at the moment that role needs it:
`.claude/skills/forge/SKILL.md`, `.claude/agents/forge-engineer.md`,
`.claude/agents/forge-auditor.md`. Each of those carries its own compressed
form of the rule that fires in its procedure; this is where the mechanism is
kept whole.

The single idea underneath all five: **a number is not evidence because it
is precise, because it was really measured, or because it came out the way
you expected. It is evidence only when it can be shown to be about the
thing under test.**

Each rule carries the incident that produced it — a reader arriving here
has no memory of it, and a rule without its mechanism erodes into ritual —
and cites where that incident is recorded, as `email-builder: <file> §X`.
Those evidence files live in the governed project's repository, not this
one: PID §9 forbids importing a governed project's content, and a pointer
is not content.

## Voice

**A claim you measured and a claim you inferred must not read alike.**

Observed (email-builder: `EDITOR-413-JSON-LEAK-2026-09-02.md` §E): a PID
stated that four affected form submissions were "ordinary buttons on the
editor page". Three of them were. The fourth was reachable by no browser
gesture at all. The rest of that PID section had been measured — the author
had driven real requests to establish it — and that one line had been
inferred from reading a template. Both were written in the same flat
declarative voice, so nothing marked the inferred line as weaker than the
measured ones around it. An Engineer discovered it mid-implementation, when
the interaction it described turned out not to exist.

Inference is legitimate and often necessary. Presenting it in the voice of
measurement is what does the damage: the next reader cannot tell which
claims to re-check, so they re-check none of them. Marking it costs one
clause — "from reading the template, expected to be X; not driven."

- **When you find an unmarked inference that turns out to be wrong:** report
  it — an Engineer to the PL as a PID defect, an Auditor as a finding. Do
  not quietly work around it, and do not silently resolve it in either
  direction. The point is that the PID gets corrected, not that this one
  dispatch survives it.

## Provenance

**Name the construction path alongside the number.**

Observed (email-builder: `RAISE-SIZE-CAPS-2026-09-02.md` §G): three ways of
constructing what was described as "the same" campaign produced 75,442,
85,251 and 97,788 bytes. All three were genuinely measured — none was
estimated or fabricated. But only one construction path is the one a user
actually takes: the editor's whitespace pretty-printer runs only in the
browser, so the two figures produced without a browser were measuring an
artifact no user ever receives.

A measurement is only as authoritative as the thing it measured. "Same
thing, measured three ways" is almost always three different things. So say
what produced the artifact you measured — driven in a real browser,
generated by a server-side call, constructed by a script — not just the
number and its units.

- **When two measurements of "the same thing" disagree:** that disagreement
  is the finding, not noise to average or to pick a winner from. Establish
  which construction path a user actually takes, report that figure, and say
  explicitly that the others measured a different path.

## Attribution

**A number that includes contributions from things that were never under
test is not evidence, however precise.**

Observed (email-builder: `LIBRARY-UTF8-CORRUPTION-2026-09-02.md` §D): an
Auditor measured en-dash bytes in an exported file to prove a decoder fix.
The first run counted bytes across the whole export, including
server-rendered content that had never been affected by the bug and could
not have been fixed by the change — so the count could not distinguish a
working fix from a broken one. The Auditor caught this itself, re-ran with
the unaffected content stripped out, and added an empty-campaign control:
`head 2 bytes / 0 mojibake, base 0 / 2`. That second run was evidence; the
first was arithmetic.

State what population a measurement counts and what it excludes. If part of
it was never under test, remove that part before measuring, not after the
number looks good.

- **When you cannot cleanly separate the populations:** add a control — a
  minimal or empty case whose expected value is known — so the number has
  something to be read against. One control case is usually cheaper than
  arguing about attribution afterwards.

## Refutations

**"I tested it and it failed" is a claim, and gets the same scrutiny as "I
tested it and it worked."**

Observed (email-builder: `RAISE-SIZE-CAPS-2026-09-02.md` §G): a PL
hypothesised that a pretty-printer explained a file-size discrepancy, tested
it, measured its effect as "a few hundred bytes against a ~12,500 byte gap",
and recorded the cause as *unexplained*. Refusing to assert an unverified
hypothesis was correct, and the honest wording made the entry look careful.
The refutation itself was wrong twice over: it counted the wrong population
(it missed that the pretty-printer also runs over server-rendered content on
load) and it valued a boundary at one character where indentation made it
about 137. The mechanism had been the right explanation the whole time.

A negative result claims less, so it invites less challenge — and that is
exactly why it slips through. Sounding appropriately humble is not
verification.

- **Before recording a cause as unexplained or a hypothesis as refuted:**
  apply Provenance and Attribution above to the refuting measurement, and
  state what population you counted and what you assumed each unit was
  worth. Those are the two places this failure happened, and both are cheap
  to state.
- **When a refutation later turns out to be wrong:** correct it where the
  original claim is cited, per `docs/FORGE-NORTH-STAR.md#durable-truth`.

## Non-vacuity

**The question is not "did this pass" but "could this have passed by
accident."**

Observed (email-builder: `LIBRARY-UTF8-CORRUPTION-2026-09-02.md` §C): a fix
stopped UTF-8 corruption inside a base64-encoded blob. Had that blob
contained no multi-byte characters, every acceptance criterion would have
passed cleanly while the defect stayed live — vacuously true. The Auditor
closed this before trusting anything else, in the two moves that are the
general shape:

1. **The input still exercises the defect.** Confirm the payload, fixture
   or page actually contains the condition the fix addresses — it verified
   the served blob still carried 48 non-ASCII bytes and no escape sequences.
2. **The check can still fail.** Run the pre-change behaviour against that
   same input and observe it failing — it ran an in-browser differential
   showing the *old* expression still corrupted that exact payload.

Only after both does "it passed" carry information.

Step 2 assumes a defect existed at base. A change that *adds* a feature has
none, so the base run fails only because the feature is absent and proves
nothing — that, and only that, is the case `n/a` is for; what to substitute
for it is in `.claude/agents/forge-auditor.md` step 4.

**The same question applied to a test suite.** An Auditor established that
no pre-existing test was anchored to the shipped values by forcing the
constants to five different value pairs and confirming the suite responded.
The Engineer-side form — revert your own fix, re-run your own new tests,
report how many actually fail — is rule 14 in
`.claude/agents/forge-engineer.md`.

- **When non-vacuity cannot be established:** say so plainly rather than
  reporting a pass. Either strengthen the input until the check can fail, or
  record which gate is actually load-bearing for that criterion — frequently
  the real browser, not the test suite. A check that cannot fail is not a
  weak pass; it is not a pass at all, and for an Auditor an unresolved one
  bars a GREEN (`.claude/agents/forge-auditor.md`, Verdict rules).
